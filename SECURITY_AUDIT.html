Security Findings

CRITICAL Firebase credentials exposed in client-side code ▶

All Firebase configuration is embedded directly in the HTML source, fully visible to anyone viewing the page:

const firebaseConfig = { apiKey: "AIzaSyDo6e52Zb6y2ca3vVAW8JVgpKEJGtPE2n8", authDomain: "paivanvari2026.firebaseapp.com", databaseURL: "https://paivanvari2026-default-rtdb.europe-west1.firebasedatabase.app", projectId: "paivanvari2026", storageBucket: "paivanvari2026.firebasestorage.app", messagingSenderId: "112024049266", appId: "1:112024049266:web:9f6e57c3a6dc0d3625d4eb" };

Impact: An attacker can use these credentials to directly interact with the Firebase Realtime Database. If security rules are misconfigured (common), they could read all data, write arbitrary data (change ticket colors, inject fake announcements), or delete the database.

Fix: Firebase API keys in frontend are expected, BUT you MUST configure strict Firebase Security Rules. Set rules to read-only for public data, and require authentication for writes. Example:

{ "rules": { "nykyinenVari": { ".read": true, ".write": "auth != null" }, "tiedotteet": { ".read": true, ".write": "auth != null" } } }
CRITICAL XSS via innerHTML with Firebase data ▶

The function updateTodayColorCard() uses innerHTML to render data that originates from Firebase:

tcStatus.innerHTML = `<span class="tc-green">●</span> until ${parseInt(h)}:${m} ...`;

While h and m are derived from Date (safe), the pattern of using innerHTML throughout the codebase is dangerous. More critically, renderTickets() builds HTML via template literals with row.innerHTML using index and ticket data from localStorage:

row.innerHTML = ` <div class="ticket-row-top"> <span class="ticket-label">Lippu ${index + 1}</span> ${removeBtnHtml} </div> ... `;

Impact: If an attacker can write to Firebase or manipulate localStorage (via another XSS, browser extension, or shared device), they can inject arbitrary JavaScript that executes in the context of the page.

Fix: Replace all innerHTML with textContent for text, or use document.createElement() for structured content. Sanitize any data from external sources.
CRITICAL Insecure QR/ticket generation — Math.random() ▶

Ticket QR codes are generated using Math.random(), which is not cryptographically secure:

let qr1 = ""; for (let i = 0; i < 2; i++) qr1 += Math.floor(Math.random() * 10); let qr2 = ""; for (let i = 0; i < 8; i++) qr2 += Math.floor(Math.random() * 10);

Impact: Math.random() uses a PRNG (xorshift128+ in V8) that can be predicted if an attacker observes a few outputs. With only 10^10 possible QR combinations (2 + 8 digits), brute force is also trivial. An attacker could generate valid-looking tickets.

Fix: Use crypto.getRandomValues() for ticket identifiers, and increase entropy (use alphanumeric characters, longer strings). Ideally, ticket generation should happen server-side with cryptographic signing.
HIGH Client-side ticket forgery — no server validation ▶

The entire ticket system runs client-side. Tickets are stored in localStorage and can be freely modified:

localStorage.setItem("ticketColor", ticketColor); localStorage.setItem("colorMode", colorMode); localStorage.setItem("tickets", JSON.stringify(finalTickets));

Impact: Anyone can open DevTools and modify ticket data — change zone from "AB" to "ABCDE", set age to "Child" for reduced fare, change purchase time, or create unlimited tickets. There is zero server-side validation. A "ticket" is just JSON in localStorage.

Fix: Tickets must be cryptographically signed by a backend server. The QR code should contain a signed token (JWT or HMAC) that the validator can verify. Client-side-only tickets are inherently forgeable.
HIGH No Content Security Policy (CSP) ▶

The site has no CSP header or meta tag. This means any injected script (via XSS or compromised dependency) can:

  • Execute arbitrary JavaScript
  • Load resources from any domain
  • Exfiltrate data to attacker-controlled servers
  • Modify page content freely
Fix: Add a strict CSP via Cloudflare Pages headers. Example _headers file:

/*
  Content-Security-Policy: default-src 'self'; script-src 'self' https://www.gstatic.com; style-src 'self' 'unsafe-inline'; connect-src https://*.firebaseio.com https://*.firebasedatabase.app
MEDIUM Service Worker caches all requests — no integrity check ▶

The SW registers with sw.js and caches content. If an attacker can poison the cache (via MITM on first load, or by compromising the CDN), the malicious content persists even after the server is fixed, since the SW serves from cache.

Fix: Implement cache versioning, SRI (Subresource Integrity) for external scripts, and a cache-busting mechanism on SW updates.
MEDIUM Firebase SDK loaded from CDN without SRI ▶

Firebase modules are loaded as ES modules from gstatic.com without Subresource Integrity hashes:

import { initializeApp } from "https://www.gstatic.com/firebasejs/10.7.1/firebase-app.js"; import { getDatabase, ref, onValue } from "https://www.gstatic.com/firebasejs/10.7.1/firebase-database.js";

Impact: If Google's CDN is compromised (unlikely but possible), or if a DNS hijack redirects the domain, malicious code executes in the user's browser with full access to the page.

Fix: Add integrity attributes to script imports, or bundle Firebase locally.
MEDIUM Announcement data from Firebase rendered without sanitization ▶

The announcement handler uses textContent (safe), but if Firebase write rules are open, an attacker could inject misleading announcements:

if (latest && latest.viesti) { announcementCard.classList.remove("empty"); acText.textContent = latest.viesti; }

Impact: Social engineering — fake announcements like "Palvelu on lopetettu, siirry osoitteeseen [phishing-url]" (Service discontinued, go to [phishing-url]).

Fix: Lock Firebase write rules to authenticated admin users only.
LOW No rate limiting on ticket generation ▶

The openTickets() function can be called unlimited times. An automated script could generate thousands of "tickets" per second.

LOW Platform selection stored without validation ▶

localStorage.setItem("platform", platform) accepts any value from btn.dataset.platform. While current code only checks "android"/"ios", injecting other values could cause unexpected CSS class application.

INFO Outdated Firebase SDK (10.7.1) ▶

Firebase JS SDK 10.7.1 is from late 2023. Check for security patches in newer versions.

INFO viewport meta disables user zoom ▶

user-scalable=no, maximum-scale=1.0 prevents pinch-to-zoom, which is an accessibility concern and can hide UI manipulation from users.

CRITICAL Admin panel accessible without authentication ▶

The admin page at /admin is fully accessible to anyone. The entire admin UI HTML is served to unauthenticated users — only hidden by a CSS class .hidden that is toggled client-side after Firebase Auth:

<div id="adminPanel" class="hidden"> <!-- Full admin panel with announcement controls --> <a href="https://pvvarihsl.pages.dev" target="_blank"> Vaihda päivänväri täältä </a> </div>

Impact:

  • Admin panel structure and features fully exposed in source
  • Second admin tool URL leaked: pvvarihsl.pages.dev
  • Admin email visible after login via user.email
  • Firebase Auth is the only barrier — no server-side route protection
Fix: Serve admin page through a server-side auth check (Cloudflare Access, or a Workers function that validates the Firebase ID token before returning HTML). Never send admin UI to unauthenticated users.
HIGH Ticket page builds forgeable tickets entirely client-side ▶

The ticket display page (/ticket, 1.4MB) reads all ticket data from localStorage and renders a visual ticket with QR code. The QR image can be replaced via customQr in localStorage:

function getQrImageSrc() { const custom = localStorage.getItem("customQr"); return custom ? custom : "images/qr.png"; }

Impact: A user can set localStorage.customQr to any data URI or image URL, replacing the QR code on the displayed ticket with one pointing to any content. Combined with editable ticket data (zone, age, time), this creates a perfect forgery tool.

Fix: QR codes must be generated server-side with a cryptographic signature. The ticket page should verify the QR's authenticity before displaying it.
INFO Secondary admin tool exposed at pvvarihsl.pages.dev ▶

The admin page reveals a link to https://pvvarihsl.pages.dev for managing the daily color. This widens the attack surface — an attacker now knows two sites to target.

  • ✗ DevTools detection — No debugger traps, no console override, no timing checks
  • ✗ Text selection prevention — No user-select: none or selectstart handler
  • ✗ Copy event interception — No copy/cut event handlers

  • ✗ Bot/scraper detection — No User-Agent check, no CAPTCHA, no rate limiting

  • ✗ Watermarking — No invisible markers in HTML/CSS

  • ✗ CSS/Font obfuscation — Custom fonts loaded from public font.css

Recommendations Summary

Priority fixes (do these first)

  1. Lock Firebase Security Rules — read-only for public, write requires auth
  2. Replace innerHTML with textContent/createElement — prevent XSS
  3. Use crypto.getRandomValues() — replace Math.random() for ticket IDs
  4. Add CSP headers via Cloudflare Pages _headers file
  5. Server-side ticket signing — tickets must be cryptographically verifiable

Anti-copy improvements

  1. JS obfuscation — Use tools like javascript-obfuscator or Terser with mangle
  2. Disable right-click + keyboard shortcuts — contextmenu, Ctrl+U, F12 interception
  3. DevTools detection — debugger statement loops, element size checks, console.log timing
  4. Dynamic content loading — Load critical HTML via JS, not static markup
  5. Cloudflare Bot Protection — Enable Bot Fight Mode in Cloudflare dashboard
  6. Server-side rendering — Render ticket views server-side, not in static HTML

Note: Client-side anti-copy is always bypassable by a determined attacker. The goal is to raise the bar, not make it impossible. The real protection is server-side logic.
